## Compact Rules

### judgment-day
Trigger: "judgment day", "dual review", "adversarial review", "juzgar".
- Launch two blind judges in parallel with identical target/criteria; never review code yourself.
- Wait for both before synthesis; never accept a partial verdict.
- WARNING (real) only if normal use triggers it, else WARNING (theoretical) → INFO.
- Ask before fixing Round 1 confirmed issues; re-judge in parallel after any fix, before commit/push/done.
- Terminal states only: `JUDGMENT: APPROVED` or `JUDGMENT: ESCALATED`.
- After 2 fix iterations with remaining issues, ask the user whether to continue.

### branch-pr
Trigger: creating/opening/preparing a PR.
- Every PR MUST link an approved issue (`Closes #N`) and have exactly one `type:*` label.
- Branch name regex: `^(feat|fix|chore|docs|style|refactor|perf|test|build|ci|revert)\/[a-z0-9._-]+$`.
- Conventional commit regex: `^(build|chore|ci|docs|feat|fix|perf|refactor|revert|style|test)(\([a-z0-9\._-]+\))?!?: .+`.
- No `Co-Authored-By` trailers (matches user's global CLAUDE.md rule).
- PR body needs: linked issue, one type checkbox, summary, changes table, test plan, contributor checklist.

### issue-creation
Trigger: creating GitHub issues, bug reports, feature requests.
- Blank issues disabled — must use bug_report.yml or feature_request.yml template.
- New issues get `status:needs-review`; a maintainer must add `status:approved` before any PR opens against it.
- Questions go to Discussions, not issues.

### chained-pr
Trigger: PR >400 changed lines, stacked PRs, review slices.
- Split PRs over 400 changed lines unless maintainer accepts `size:exception`; keep each PR reviewable in ~60 min.
- One work unit per PR; keep tests/docs with the unit they verify.
- Independent slices → Stacked PRs to main. Must-integrate-together → Feature Branch Chain with draft tracker PR, child #1 targets tracker, later children target immediate parent.
- Every child PR needs a dependency diagram marking current PR with 📍; don't mix chain strategies mid-flight.

### cognitive-doc-design
Trigger: writing guides, READMEs, RFCs, onboarding, architecture/review docs.
- Lead with the answer/decision, then context. Progressive disclosure: happy path → details → edge cases.
- Use tables/checklists over prose to memorize. Chunk with headings/signposting.
- Default doc shape: title → one-paragraph summary → Quick path (numbered) → Details table → Checklist → Next step.

### comment-writer
Trigger: PR feedback, issue replies, reviews, Slack/GitHub comments.
- Start with the actionable point, no full recap. 1-3 short paragraphs or tight bullets.
- Explain the technical why when requesting a change; comment on highest-value issue only, avoid pile-ons.
- Match thread language; in Spanish use Rioplatense voseo (podés, tenés, fijate, dale). No em dashes.

### work-unit-commits
Trigger: implementation, commit splitting, chained PRs, keeping tests/docs with code.
- Commit by deliverable work unit, never by file type (no separate "models"/"services"/"tests" commits unless each stands alone).
- Keep tests and docs in the same commit as the behavior they verify/explain.
- If SDD tasks forecast >400 changed lines, group commits into chained-PR slices before implementing; follow the resolved `delivery_strategy`.

### skill-creator
Trigger: creating new skills, agent instructions, documenting AI usage patterns.
- Skill body target 180-450 tokens (max 1000); templates/schemas go in `assets/`, conceptual detail in `references/`.
- Frontmatter requires `name`, `description` (one line, trigger words first, ≤250 chars), `license`, `metadata.author`, `metadata.version`.
- Section order: Activation Contract, Hard Rules, Decision Gates, Execution Steps, Output Contract, References.

### playwright-cli
Trigger: browser automation, testing web pages, Playwright.
- Snapshot-driven: `playwright-cli snapshot` gives refs (`eN`) to target with `click`/`fill`/`type`; prefer refs over raw CSS selectors when available.
- Prefer WebMCP tools (`webmcp-list`/`webmcp-call`) over UI-driving when a page registers them for the task.
- On Windows, escape `&` in URLs (`^&` in cmd.exe, `--%` in PowerShell) or it truncates the query string.
- Not relevant here today (no Playwright/E2E setup in this repo) — install via `npm install -g @playwright/cli@latest` if E2E coverage is added later.
